## Keys and storage

Choose app-directory `.dev.vars` or `.env`, never both. The filename validator
rejects mixing their variants and does not read secret values. The `.env`, `.env.*`, `.dev.vars` and `.dev.vars.*` patterns are ignored,
except the committed `.dev.vars.example`.
The fresh replay needed no secret file. Never transfer such files or CMS state
between tasks. Neither root legacy environment actions nor a build system's secret
settings automatically configure the deployed Worker runtime.

## Findings at the initial revision

1. Development startup generates untracked `apps/astro-emdash/emdash-env.d.ts`.
   This path is not ignored, and Prettier rejects its generated formatting. A fresh
   check/build run passes lint, but a later dev session can dirty the worktree and
   break lint. Coordinate an ignore/formatter policy fix with the foundation owner.
2. No committed CI workflow runs migration checks. Existing public legacy preview
   builds are user-approved and useful legacy evidence, but do not prove migration
   check/build/smoke passed. Add an exact-SHA gate covering frozen install, lint,
   both application checks/tests/builds, local migration smoke and legacy dry-run.
3. `LOCAL-SEED.md` still says schema seed is not selected, while app package metadata
   now selects it. Its later remaining-gate text also predates CMS D1/policy tests.
   Reconcile it with `RUNTIME.md`; never introduce a public fixture fallback.
   PLAN's foundation test counts remain historical evidence, not current totals.
4. Saved/checked-in environment actions still run legacy dev/check/build. A future
   environment update should activate the toolchain, verify the chosen integration
   SHA and run shared bootstrap, then expose separate migration check/build/smoke
   and supervised start actions. Preserve the legacy actions during migration.
5. UI integration must prove published CMS rendering and generic HTTP 503 without
   fallback, then repeat content, links, responsive, accessibility and visual parity.
6. Real admin/passkey registration/login, authenticated editing, authorized draft
   preview, publish, media picker/replacement, logout and session behavior remain
   unverified. Setup HTML 200 and direct test-handler calls are insufficient.
7. The importer is still a disposable rehearsal, without an approved persistent
   target import/publication procedure. Define reviewed single-writer setup,
   conflict handling and recovery before touching a persistent CMS database.
8. Private preview resources, stable origin, access restrictions, runtime secrets
   and least-privilege deployment credentials need separate approved setup. Build
   the explicitly selected target and inspect generated binding config before
   publishing. Keep DB/MEDIA/SESSION separate from production and legacy resources.
9. Recovery needs a rehearsed runbook: named operator; cutover stop/go criteria;
   recorded last-good legacy artifact/config; consistent D1/R2 backups; secure
   encryption-key recovery; restoration to isolated resources; content/media/auth
   verification; handling of edits after cutover; and a bounded rollback decision.
   Rolling back code alone does not restore database schema/content or media.
   Main/domain routing and production remain separately approval-gated.
